## 代码风格：一律用显式 for 循环，不用推导式 / lambda / 三元表达式

⚠️ **2026-09-15 起，新写的 Python 代码一律不用列表/字典/集合推导式（ListComp/DictComp/
SetComp）、生成器表达式（GeneratorExp）、`lambda`、三元表达式（`X if Y else Z`）**——不管是
人写的还是 AI/agent 写的。原因是维护者本人看不懂这几种写法，这几种写法在改动之前的
仓库里出现了 **645 处**（81 个文件，2026-09-15 用 AST 扫描核实，已排除 `migrations/` 等目录）
——这是"可读性优先于简洁"的明确选择，不是代码洁癖，**不要在 review 里把代码改回推导式**。

- **范围**：仅 Python 后端代码，不含 `**/migrations/**`（历史记录，禁止改动，见上一节）。
  前端 Vue/JS 不在此列，另行讨论。
- **换法**：推导式/生成器表达式 → 先声明累加容器（`= []` / `= {}` / `= set()`），显式 `for`
  循环，循环体内 `if` 判断，`.append()` / `[k] = v` / `.add()`；`lambda` → 有名字的 `def` 函数。
  **只许变形状，不许变行为**——同一份输入必须产出同一份输出，这是纯风格重写，不是逻辑重写。
- `sorted(..., key=lambda ...)` / `list.sort(key=lambda ...)`：`lambda` 换成一个具名 `def`
  （函数名要体现排序依据，如 `_by_order_then_id`），**不要把排序算法本身也重写一遍**。
- 🚨 `any(...)` / `all(...)` 包一层生成器表达式：展开时**必须保留短路语义**——用一个布尔
  标志位 + `break`，不能无条件跑完整个循环再判断，否则短路带来的提前退出会被悄悄改成
  "跑到底"。
- 三元表达式出现在函数调用参数、字典 value、f-string 内部时**不能原地展开**（那些位置
  只能放表达式，放不进 `if`/`else` 语句）：先在外面用 `if`/`else` 算出一个有名字的临时变量，
  再把这个变量传进去 / 放进 f-string。
- 嵌套推导式、多个 `for`/`if` 子句的推导式，按子句原有顺序原样映射成嵌套的 `for`/`if` 语句，
  **不改变遍历顺序**。
- ⚠️ **手写 `for` 循环会让循环变量泄漏到函数其余部分（推导式不会）**：展开前检查该变量名
  是否在同一函数里被其它地方复用（另一个 for 循环的目标、别的推导式、闭包捕获），
  有复用就要确认"两次绑定之间没有代码会读到泄漏的旧值"，拿不准就换一个更具体的名字。
- 🚨 **改完必须用同一套 AST 扫描重新跑一遍，确认排除范围之外的计数是 0**，
  且 `git diff --stat -- '**/migrations/'` 必须为空、`manage.py makemigrations --check --dry-run`
  必须是 `No changes detected`——纯风格重写不能带出任何行为差异，也不能误碰 migration。

## Architecture

This is a decoupled (front-end/back-end separated) web application, not a traditional server-rendered Django site:

- **`klfilter_web/`** — Django project config (settings, root URLconf, WSGI/ASGI entrypoints).
- **`core/`** — Django app. It does **not** serve any HTML front end; its only job is to expose JSON API endpoints under `/api/` (see `core/urls.py`, mounted via `path('api/', include('core.urls'))` in `klfilter_web/urls.py`). Views use Django REST Framework's `@api_view`.
- **`frontend/`** — Standalone Vue 3 + Vite SPA that is the actual front-of-site UI (details in **Frontend architecture** below). It talks to the Django API through a **shared axios client** (`frontend/src/api/index.js`) whose `baseURL = import.meta.env.VITE_API_BASE_URL` — set to `http://localhost:8000/api` in `frontend/.env.development` and to the **relative `/api`** in `frontend/.env.production` (production is same-origin behind one domain, so **no CORS needed**). Call sites use it like `api.post('/contact/', …)` (see `Contact.vue`). Runs on its own dev server (port 5173), independent from Django. `django-cors-headers` (`CORS_ALLOWED_ORIGINS` in `settings.py`) still allows the Vite dev origin (`:5173`) to call the Django API during local development.
- Django's admin (at `/admin/`) is the only server-rendered part of Django still in use, themed with `django-simpleui` (must be listed **before** `django.contrib.admin` in `INSTALLED_APPS`). **后台界面是中文，但 `LANGUAGE_CODE` 是 `'en'`**（2026-09-11 起，它决定公开站哪门语言不带网址前缀）——后台由 `adminui/middleware.py:AdminChineseMiddleware` 单独钉成 `zh-hans`，详见「三语分路径」一节。
- **`settings.py` is environment-variable driven** so the same code runs locally and in production: `SECRET_KEY`, `DEBUG` (`DJANGO_DEBUG`, default `True`), `ALLOWED_HOSTS` (`DJANGO_ALLOWED_HOSTS`, comma-separated), and all DB params (`DJANGO_DB_NAME/USER/PASSWORD/HOST/PORT`) read from `os.environ` with local-dev defaults. `CSRF_TRUSTED_ORIGINS` lists the two `https://…kl-filter.com` origins. A `if not DEBUG:` block enables HTTPS security (`SECURE_PROXY_SSL_HEADER` for the reverse proxy, SSL redirect, secure cookies, HSTS). `STATIC_ROOT = BASE_DIR/'staticfiles'` for `collectstatic` (admin/simpleui assets, served by nginx in prod).
- Database is **MySQL 8.0** (switched from the original SQLite). **Local dev**: `127.0.0.1:3306`, user `root`, **empty password** — a portable ZIP install at `D:\mysql\mysql-8.0.40-winx64` (config `my.ini`, data dir `data/`), auto-start Windows service **`MySQL`** (`Start-Service MySQL` / `Stop-Service MySQL`; CLI at `D:\mysql\mysql-8.0.40-winx64\bin\mysql.exe -u root`). **Production**: a `mysql:8.0` Docker container on 阿里云轻量 with a real password from `.env` (see **Deployment** below). The old `db.sqlite3` is unused.
- `core/models.py` defines the `Contact` model (DB table **`contact`**) backing the frontend contact form — fields: `name` 联系人, `email` 邮箱, `phone` 电话, `inquiry_type` 咨询类型 (choices general/distributor/oem/support), `message` 留言内容, plus auto `created_at` 提交时间. Registered in `core/admin.py` (shows as 联系表单 in the admin). The frontend Contact form (`frontend/src/views/Contact.vue`) POSTs to it live: `POST /api/contact/` (`core/views.create_contact` + `core/serializers.ContactSerializer`) validates and writes a row, returning 201; the form maps its `inquiryType` value to the `inquiry_type` field and shows localized success/error states.
- **Products are database-backed** (migrated out of the old static `data/products.js`, which is deleted). `core/models.py` defines `Category` (`product_category`), `Product` (`product`), `ProductImage` (`product_image`, gallery: kind `main`/`gallery`/`exploded`). Bilingual = **paired columns** `*_zh` (required) / `*_en` (optional; API falls back zh↔en). Repeated fields (`features/certifications/applications`) are **one-item-per-line TextFields**; `specs` are `标签: 值` per line — the API splits them into arrays / `{label,value}` (see `core/serializers.py` helpers `to_lines`/`to_specs`). Read-only DRF endpoints (`core/views.py`): `GET /api/categories/`, `/api/products/?category=<slug>`, `/api/products/<slug>/`, all localized via `?lang=zh|en`; image URLs are **relative `/media/...`**. **`price` 与 `short_description_*` 四列已于 2026-09-11 从 `Product` 上删除**（迁移 `0007`）。价格自 2026-08-03 起就完全不对外，简介则早已不在任何页面上渲染（产品卡片只有图片和名称，详情页那段文字一直取的是 `full_description`），只剩 SEO 的两处用途，现已一并改用 `full_description`——`seo/views.py` 的 meta description、`seo/render.py` 的注入正文、`fill_product_copy` 的去重守卫、`deploy/gsc_daily.py` 的重复文案检测，**四处全部盯 `full_description`**。全站不再有「产品价格」与「产品简介」这两个概念；`Category.short_description_*` 是另一回事，首页分类卡片上那段文字就是它。Admin (`core/admin.py`) uses `django-import-export` (`ProductResource`, id=slug, `category` column = category slug) for **Excel/CSV bulk import/export**, plus a `ProductImage` inline.

      偏离 8:3 超 ±3%、或宽度 < 1920 的上传。这是 2026-08-05 定的：此前不限比例，三张图分别是
      1.49 / 2.33 / 1.79:1，而展示带是固定比例，`object-fit: cover` 必然裁掉 27%~53% 的高度。

      5 组里有 4 组（`FC-35` `FC-35-22-QP` `FC-44` `FC-45`）**共用编号恰恰是因为
      它们是同一型号的不同滤料**——这条规则挑出来的正好是这次要拆掉的那一类。
      现在要求**成员名称里能解析出至少两个不同的长度**才自动建组
      （复用 `productimages/scaling.py:parse_length_mm`，与图片比例同一套判断）。
      实测判定全对：`FC-65`（10" vs 20"）照常建组，那 4 组全部被拦下。
      ⚠️ 同时排掉了 `code` 为空的产品——「编号完全相同」对空编号也成立，
      旧规则会把全屋净水器那 15 个空编号产品归成一个 15 人的组。
    - **`group_key` 留空 = 不参与分组**，前台照常单独显示。默认必须安全。
    - **规格标签从产品名的差异里抽**（`derive_labels`）：这些组的编号本来就相同，
      回退到编号会得到三个一样的「FC-35」，等于没标。两个坑有测试盯着：
      ① 切点必须退到非字母数字边界，否则 `10"`/`20"` 会被切成 `1`/`2`；
      ② 一组里只要有一个抽不干净就整组留空，不要三个空 + 一个塞满长句。
    - **列表页卡片上没有「N 种规格」角标**（2026-09-03 删掉）。合并成一页之后卡名本身
      就写着尺寸范围（`FC-53 … 10"-20"`），角标是同一件事说两遍。
      `collapseVariants` 因此也不再往产品对象上挂 `variantCount`。
      ⚠️ 代价：**不是「同系列不同尺寸」的组在列表页没有任何提示**（`FC-44` 是三种滤料、
      `FH-11` 那组四个都是 10" 只差接口），唯一入口是详情页主图下方那条切换条。
    - 后台两个入口：独立菜单「产品变体分组」批量填，以及产品编辑页里的 inline
      （挂在 `adminui/admin.py`，因为 `ProductAdmin` 在 `core/` 里不能改）。
  - **`downloads/`**（2026-08-06 起）— 前台 `/downloads` 的技术文档下载页（后台分组「技术文档」）。
    `Document`（`downloads_document`）：双语成对列 + `file` / `version` / `published_on` /
    `order` / `is_visible`，**平铺一个列表不分组**（文档不多时最好找；要分组再加一张分类表）。
    `GET /api/downloads/?lang=`、`GET /api/downloads/<id>/file`（后者计数后 302 到 `/media/`）。
    - **计数必须用 `F('download_count') + 1` 的 `.update()`**，不能写成读-改-写，
      并发下会丢计数（`downloads/tests.py` 有测试盯着连续 5 次必须正好加 5）。
      下架（`is_visible=False`）的文档一律 404，否则「取消显示」形同虚设。
    - **允许的扩展名刻意不含 `html`/`svg`/`xml`**：它们与站点同源、浏览器会当文档渲染，
      等于开一个储存型 XSS 的口子。
    - **`file` 字段 `max_length=255`**（默认 100 不够）：`downloads/202608/` 前缀就占 17 个字符，
      技术文档的文件名常有四五十个，超了会在写库时报 `DataError`。
    - **`file_size` 存成列**而不是每次读 `file.size`——后者每一行都要访问一次存储；
      `save()` 里刷新，换文件后会重算。
    - **单文件上限 50MB（`MAX_FILE_MB`）与 `deploy/nginx.conf` 里 `location /admin/` 的
      `client_max_body_size 52m` 是一对**。后台上传走 `/admin/`，nginx 那层先拦，
      调小了同事会看到浏览器的 413 而不是表单里的友好提示。server 级的 `10m` 保持不动——
      只有后台需要大请求体，公开接口不该跟着放开（实测判据：12MB POST 到 `/admin/` 不是 413，
      到 `/api/products/` 必须是 413）。
    - 前端下载按钮用 **`<a download>`**：同源下浏览器直接存盘而不是在线打开 PDF，
      且经过同源 302 之后依然有效，**不需要在 nginx 设 `Content-Disposition`**。
    - 已知取舍：后台换文件时**旧文件不会自动从磁盘删除**（Django 默认行为），
      `media/downloads/` 会堆积孤儿文件；下载次数**包含爬虫**（`robots.txt` 的
      `Disallow: /api/` 已覆盖该端点，但不守规矩的照样算），看趋势可以，别当精确值。
## 滤壳的规格表（2026-09-02 起，`homepage/data/housing_specs.json`）

滤壳三个分类（单/双 O 型圈、不锈钢，51 个产品）的 `specs_*` 原本是
`product_source/filter housing offer list.xlsx` 里 `MATERIAL LIST` + `PARTS` 两列的原文，
也就是**报价单的 BOM**——「FH-16 滤壳 1/2" 铜接口」「白色内盒」这类报价条目，
是工厂核价用的，不是买家选型看的；中文那份还是机器翻的，材质行首尾相接重复了一遍。
现已按 `滤壳规格和性能描述.xlsx` 那张表重写，由 `fill_housing_specs` 落库
（数据是单一事实来源，默认只出报表、`--apply` 才写、幂等、只碰那两列）。

- **分组标题的编码是「有标签、值为空」的行**（`材质清单:` / `接口规格:` / `技术参数:`），
  续行则是「无标签、有值」。`core/serializers.py:to_specs` 一个字没改，
  由渲染层识别成跨两列的行——**`frontend/src/components/ui/SpecTable.vue` 与
  `seo/render.py:_spec_rows` 必须同构，改一边就要改另一边**（前台与注入不一致就是 cloaking）。
  这两种退化行以前渲染成空白的 `<th>` / `<td>`，线上 fh-16 那页难看正是因为它。
- **🚨 规格里绝不写 mm**。`productimages/scaling.py:parse_length_mm` 的**第一条**规则
  就是找 `(\d{3,4})\s*mm`，命中即停；滤壳现在靠的是第四条（名称里的英寸）。
  写一行「高 320mm」会静默改掉整个分类的图片显示比例与 `sort_products_by_size` 的排序。
  命令的自检直接拦这个模式，`homepage/tests.py:HousingSpecsTests` 盯着。
  同理，**写了 `cartridge` 就必须写 `nominal_size`**——不然「10" × 2.5"」里的 `2.5"`
  会被第四条规则抠出一个 `5` 当长度。
- **压力两行刻意空着**：xlsx 里「Brust pressure」空白、「Max working pressure」只有一句
  `*follow NSF42 standard…*` 脚注，没有数值。没数据就不写，**也不写那句脚注**——
  产品页出现 NSF 字样与全站「认证必须标持证方」的口径打架。工厂给了数值再往 `SECTIONS` 加行。
- **工作温度只在有依据时写**：`4-45 °C` 属于 PP/AS 瓶身 + NBR O 型圈这一族；
  `fh-21` 是尼龙 + EPDM 热水壳，产品名里写着 <125 °C；不锈钢壳与 `PF-22` /
  `fh-45-6` / `fh-46-6`（报价单里没有材质列）整行省略，不编。
- ⚠️ **`fh-21` 的标称尺寸不是从报价单来的**（那上面没写），是同事 2026-08 在后台自己补的
  「尺寸: 10" (254 mm)」。第一版重写把它丢了，`parse_length_mm` 随即从 254.0 掉成 None——
  上线时靠「部署前后逐个比对 420 个产品的解析长度」当场发现。现在写成 `10" 细身（slim）`：
  第四条规则从 `10"` 同样算出 254.0，而写 `254 mm` 会抢在第一条命中。
  **教训是「同事在后台补过的内容会被这类批量重写静默抹掉」**——改这类字段前先扫一遍
  快照里有没有非标准标签（本次实测 51 个滤壳里只有 `fh-21` 这一处）。
- 两处**待工厂确认**的地方：① 压力数值；② 不锈钢壳的 O 型圈材质——报价单里
  `fh-31/32` 系列写 `silicon o-ring`，两个 BB 型号写 `NBR silicon o-ring`，现统一按「硅胶」写。

2026-09-04 对滤芯子树（87 个产品）做过一次体检，查出三件都在线上的问题，
由两条命令分别收拾。**两条互不依赖，谁先跑都行**。

- **🚨 13 个已发布滤芯的规格表里印着美元单价**（`US$ 0.8~6.2`，中英文都有，
  注入给爬虫的正文里也有），是从报价单原样粘进来的。仓库口径是价格一律不对外
  （`price` 字段本身已于 2026-09-11 删除），这里绕过字段直接写进了规格文本。
  ⚠️ **这件事与 `price` 字段是两回事**：`strip_spec_prices_weights` 收拾的是
  `specs_*` 文本里印着的美元单价，删字段不影响它，那条命令与它的测试全部保留。
- **克重**：滤芯口径规定不标重量。两种形态都删——写在「规格」行里的整支重量
  （`508mm/…/240g/5um`）和写在「材质/备注」行里的填充量（`材质: 300g 煤质颗粒活性炭`）。
  共 18 个产品，含「未分类」里的 `fc-62-20`。
- 以上两件由 `strip_spec_prices_weights` 处理，**纯规则、不带数据文件**。
  因为它只删不改写，自检里有一条很强的不变量：**结果必须是原文的子序列**
  （只允许删字符与合并空白），哪条正则一旦改写了别的内容立刻被拦下。
  - ⚠️ **克重的 `g` 必须区分大小写**：`75GPD`（产水量）、`GAC` 里都有大写 G，
    用 `re.I` 会把产水量削掉，有测试钉着那一行一个字不能变。
  - ⚠️ 收尾规则**只收拾自己造成的空白**。第一版多写了 `([:：])\s+ -> `，
    把每个标签后面的空格都吃掉（`材质:煤质…`）——渲染出来一样
    （`to_specs` 两边都 strip），但库里样式平白改一遍，diff 全是噪音。

- **机翻残留**：中文规格当年只译了一半，**70 个产品（80%）夹着英文词**，
  客户直接看得到：`材质: 煤质活性炭棒 inside with PP 端盖`、`备注: empty 滤壳`、

  由 `translate_cartridge_specs` 按 `homepage/data/cartridge_specs_zh.json` 落库，
  **只碰 `specs_zh`**——`specs_en` 是原文与语义依据，一个字不动。
  - **译文是起草出来的，落库前机器验四条**，任何一条不过就拒绝写库：
    slug 必须在库里、行数不变、每行标签逐字相同、**每行的数字序列逐字相同**
    （尺寸/精度/目数/碘值都是买家要核验的，翻译只许动文字）。
    另外拦下「又把报价或克重写回来」和「白名单之外的英文词」。

    所以与那条命令**没有先后依赖**。
  - 译法约定：`O/D` / `I/D` / `ID` / `OD` 保留英文不译；`length` → 长度；

## 滤芯分类树（2026-08-10 起，权威来源是《滤芯的分类.xlsx》）

分类结构与文案由 `homepage/management/commands/restructure_cartridge_categories.py` 的
`TREE` 定义，产品归属由同文件的 `FAMILY` 定义。**改分类先改这个文件再跑命令，不要在后台手改**
——后台改完下次跑命令会被覆盖回去，而且 slug 与文案就没有单一事实来源了。
命令默认只出报表，`--apply` 才写库；幂等。

```
滤芯 filter-cartridges-group
├─ 粗滤滤芯 sediment-filters          └ 熔喷 spun-pp-filters / 线绕 pp-string-wound-filters
│                                       / 折叠 pleated-filters / 网式 mesh-filters / 陶瓷 ceramic-filters
├─ 活性炭与树脂 carbon-resin-filters   └ CTO cto-filters / GAC gac-filters / 树脂 resin-filters
├─ 后置滤芯 post-filters               └ 2 吋 post-filters-2inch / 2.5 吋 post-filters-2-5inch
│                                       / 2.5 吋一触式 one-touch-filters
├─ 介质滤芯 media-filters              └ 可换介质 refillable-media-filters / 填充介质 filled-media-filters
└─ PAC 复合滤芯 pac-filters（无子分类，直接挂 5 个产品）
```

- **🚨 有子分类的分类不能挂产品**。`Products.vue` 全页只有一条规则：*有子分类 → 只列子分类卡片；
  没有 → 列产品*。所以父分类自己挂的产品**在前台完全不可见，且没有任何报错**。
  2026-08-06 踩过一次，74 个产品被整体挡住。命令里有守卫（未命中的产品若停在父分类里就
  拒绝 `--apply`），`homepage/tests.py:TreeShapeTests` 也盯着。
- **归类依据是产品编号，不是产品名称**。`FAMILY` 把 `FC-<数字>` 的数字映射到分类，
  直接照抄分类表。上一版按 `name_en` 猜材质，结果网式/陶瓷/树脂三类根本没有分类可去，
  被兜底规则静默塞进了「可换介质滤芯」。**取的是整个数字**，所以不存在
  「FC-5 的规则会不会吃掉 FC-58」这种顺序陷阱。
- **没有兜底分类**。编号不认识就留在原分类并在报表里单独醒目列出——静默吞掉正是上一版的问题。
  同事录入新型号时若编号族不在 `FAMILY` 里，会出现在这一段，补一行映射即可。
- **PAC = PP + Activated Carbon 复合，不是粉末活性炭**（2026-08-10 用户订正）。
  判据在产品本身：FC-7 / FC-58 的英文名就是 `5um PP + GAC coconut`。
  分类名一度写成「PAC 粉末活性炭滤芯」，整段简介也跟着写错了。有测试盯着别改回去。
- 改完分类**必须补跑 `compute_image_scales`**——显示比例的基准是「同分类内最长产品」，
  分类一变基准就变（见下一条）。
- 分类 slug 2026-08-10 统一成小写连字符、叶子一律 `-filters` 结尾。
  分类**不进 sitemap**、前端与 nginx 也没有硬编码，所以改 slug 只影响别人手上已分享的
  `/products#<slug>` 深链——会落回默认分类，不会 404。**产品 slug 完全是另一回事**：
  那是真实网址且在 sitemap 里，不要动。
- **分类配图缺口（2026-09-01 实测，基本补齐了）**：`homepage_categorycard` **41 条
  （= 全部分类都有行，`seed_category_cards` + `homepage/signals.py:autocreate_card` 的结果），
  其中 39 条有配图，只剩 2 条空**：`commercial-ro-system`（商用反渗透纯水机）与
  `uncategorized`（未分类）。**这两个分类本身就是 0 产品的空分类**，所以前台也看不到占位图。
  需要 **16:9、建议 1600×900**。（缺口变化：08-10 缺 17 → 08-13 缺 5 → 09-01 缺 2，同事一直在补。）
- **✅ 新增/删除产品图后会自动重算显示比例（2026-08-12 起），不再需要人工补跑命令。**
  `productimages/signals.py` 在 `ProductImage` 的 `post_save` / `post_delete` 上挂了
  `transaction.on_commit`，重算该产品**所在整个分类**（新图可能成为分类内最长的那个，
  基准一变同分类其它产品的比例都要跟着改）。逻辑抽在 `productimages/scale_sync.py`，
  与 `compute_image_scales` 命令共用同一份，避免两处分叉。
  - **`try/except` 必须写在 `on_commit` 回调内部**——回调本身抛异常会冒泡成 500，
    包在信号函数体里挡不住。沿用本 App 的 fail-open 原则：重算出问题绝不能让员工
    传不上图、删不掉图。
  - 清理过期记录时**显式按 `category_id` 限定范围**。信号是逐分类触发的，
    不限定的话 `exclude(product__in=本分类产品)` 会把其它分类的记录一并删掉。
  - `is_manual=True` 的行不覆盖 `scale`（诊断字段仍刷新），与命令规则一致。
  - 起因：两天内连续两次踩到同一个静默问题——`FC-3`（08-10）与 `FC-4`（08-11）
    在后台新增后没人跑命令，前端对没有记录的产品按 1 处理、满格显示，
    252mm 的滤芯被画得和 508mm 的一样高，**而页面不会报任何错**。靠文档提醒人工补跑
    显然不可靠，所以改成信号自动接管。
  - 命令仍然保留，**重复执行是安全的**（实测只补缺失、既有数值零变化、不覆盖人工设定），
    改完分类树等批量操作后仍应手动跑一次。

- **缩略图的大小关系跟着实物走。** `compute_image_scales` parses each product's real length (four rules, in priority order: `规格` 里的 mm → `L:xx"` → RO 型号编码如 `4040`=4"×40" → 名称里的英寸; 144 有图产品命中 140) and sets `scale = 该产品长度 / 基准长度` — **基准是分类内统一而非全站**（全站跨度 1:8.1，最小的只有 12% 高看不清；分类内只有 1:2~1:4，而产品页本来就按分类分组）。`trim_product_images` 先把抠图的多余白边裁掉，让「图片长边 = 产品长边」，比例才准；带背景的实拍照（RO 膜）自动跳过。
  - **🚨 滤芯与滤壳两棵树的比例再过一道压缩曲线**（2026-09-04 起，
    `scale_sync.py:DISPLAY_GAMMA = 0.5`，即真实比例开方后再画）。
    起因：`single-o-ring-housings` 列表页可见的 26 个产品里，5" 九个画 0.25、
    10" 十四个画 0.50——**24 个被压在半格以下，只为了迁就 2 个 20"**，5" 那批看不清。
    开方后 5" 画 0.50、7" 0.59、10" 0.71、20" 仍是 1.00：大小顺序一点没变，
    小件不再小到看不清。曲线是单调的，**不会打乱顺序**，最长的那个仍然满格。
  - **范围只有这两棵树**（`GAMMA_ROOTS`），用户 2026-09-04 明确限定。
    其余 7 个一级分类仍是严格的真实比例——`runxin-automatic-filter-valves` 里那个
    被 `MIN_SCALE` 压到 0.18 的阀门**保持 0.18**。判断走祖先链（`Category.ancestors()`），
    所以三级分类也命中；查不到分类时返回 False，失败方向落在「保持原样」那一边。
  - **`length_mm` 不受曲线影响**，仍然是如实解析出的长度。曲线只作用在「画多大」，
    以后重调 γ 或改范围只要改常量重跑命令，不用迁移数据。
    `productimages/tests.py:DisplayGammaTests` 盯着范围与单调性两件事。
  - **🚨 基准取「这一页上真正显示出来的产品」里最长的那个，不是分类里最长的那个**（2026-08-27 修）。
    列表页对同一变体组只渲染代表款，被折叠掉的产品**根本不出现在页面上**，不该参与基准。
    此前把它们也算了进去，后果是**整页产品集体缩水一半**：`spun-pp-filters` 页面上 4 个产品全是 10"，
    却因为组里那个不显示的 20"（`FC-53-20"`）把基准顶到 508mm，全部按 0.496 画，
    **而页面不会有任何报错**。实测 7 个分类 19 个产品中招（熔喷 / PAC / 线绕 / 可换介质 /
    GAC / 树脂 / 不锈钢滤壳）。判据很直观：**一页里最大的那个产品必须占满画框**。
    折叠规则抽在 `variants/folding.py:hidden_product_ids()`，**必须与前端
    `frontend/src/api/products.js:collapseVariants` 一致**（代表款 = 组内 `order` 最小、
    同 order 按 slug 字典序；只在已发布产品里选，因为前端拿不到未发布的），
    改一边就要改另一边，`variants/tests.py:HiddenProductIdsTests` 与
    `productimages/tests.py:BaseExcludesFoldedVariantsTests` 两头盯着。
    ✅ **2026-09-03 起改变体分组也会自动重算**（`productimages/signals.py` 的
    `auto_scale_on_variant_save` / `_delete`）。此前信号只挂在 `ProductImage` 的增删上，
    同事在后台把产品移进/移出分组后，代表款一变基准就变，却没人重算——
    实测未挂信号时 10" 那款会停在 0.496，正是「整页缩水一半」那个老症状。
    `productimages/tests.py:VariantChangeResyncsScaleTests` 盯着（三条用例在拆掉
    信号后全部转红，不是空跑）。
    ⚠️ **仍然存在的缺口**：`core.Product` 的 `is_published` 切换与换分类同样会改变基准，
    这两条没有信号——要挂得在 `pre_save` 里比对旧值、只在真变了时才排队，
    否则批量导入会在一次事务里排上几百个重算。改完这类操作仍应手动跑一次
    `compute_image_scales`（⚠️ 它**默认就写库**，只报告要加 `--dry-run`）。
  - `compute_category()` 返回 `(rows, base)`——base 一并返回是为了让命令打报表时
    不用从 rows 反推（反推会把被折叠的产品又算进去）。报表里「最大 X = 508mm (比例 1.00)」
    这种看着矛盾的行是正常的：那正是被折叠、比基准还长的产品，`min(1.0, …)` 把它夹住了，
    而它并不渲染在列表页上。
- **产品在分类内的排序：尺寸小→大，同尺寸按编号自然序**（2026-08-27 起，
  `homepage/management/commands/sort_products_by_size.py`）。
  `Product.Meta.ordering` 用的是 `order` 字段，而它默认 0、同事建产品时基本没填，
  于是同分类内实际按 `id`（**录入先后**）排。图片比例修好之后这个问题就很刺眼了：
  `single-o-ring-housings` 原来第一行是 10" → 5"迷你 → 10"，第二行两个 20" 巨物，
  第三行又缩回 10"/7"/7"，大小全程锯齿状跳动。已重排 8 个分类 82 个产品。
  - **尺寸按 3% 容差分档**：252mm 与 254mm 都是名义 10"，视觉上没有区别，
    不设容差 `pp-string-wound-filters` 的 FC-4(254) 会被判成「该排最后」，那是假错位。
  - **解析不出长度的排到该分类最后**并在报表里点名（实测 2 个：`FH-21`、`ULP-440`）。
    补完「规格」重跑就自动归位。
  - **命令只处理白名单里的分类**。全站一把梭会顺手改掉配件/仪表/阀门那些
    规格栏全空、主序根本判不了的分类，把它们从「按录入顺序」变成「按编号顺序」
    是另一个决定，别混在一起。
  - 排序覆盖分类内**全部**产品、不特判变体折叠——列表页只渲染代表款，
    而筛选保持相对顺序，所以给全部产品排一遍，代表款自然就是对的顺序。
- **`REST_FRAMEWORK = {'DEFAULT_AUTHENTICATION_CLASSES': []}` in `settings.py` is load-bearing** — do not remove. 本站 `/api/` 全是公开接口。留着 DRF 默认的 `SessionAuthentication` 会导致一个极隐蔽的 bug：浏览器一旦带着已登录的 admin session cookie，DRF 就强制校验 CSRF token，而 SPA 的 axios 不带这个 token → **登录过 `/admin/` 的员工提交联系表单必定 403，没登录的访客却正常**。线上曾连续 7 次提交全部 403、0 次成功。

## Frontend architecture (`frontend/src/`)

- **Trilingual (English + Simplified Chinese + Spanish) multi-page marketing SPA.** `main.js` installs `router` and `i18n` on the app; `App.vue` renders `<AppHeader/>` + `<router-view/>` + `<AppFooter/>`. Routes (`router/index.js`, all eagerly imported; Vite `@` alias → `src`): `/` Home, `/products` Products, `/products/:slug` ProductDetail (`props: true`), `/faq`, `/about`, `/contact`, catch-all → NotFound. `scrollBehavior` resets scroll to top on navigation.
- **Components**: `components/layout/` (AppHeader = brand + nav + LanguageSwitcher, collapsing to a hamburger under 768px via CSS; AppFooter) and `components/ui/` (AccordionItem, ImagePlaceholder, SpecTable — pure presentational, they render whatever already-localized strings the caller passes).
- **Content split**: **Products/categories come from the Django API** (see Architecture) — `Home.vue`, `Products.vue`, `ProductDetail.vue` fetch async via `frontend/src/api/products.js` (`fetchCategories/fetchProducts/fetchProduct`, built on the shared `@/api` axios client), passing the current locale as `?lang=`. Product **image URLs** are relative `/media/...`; `api/products.js` prepends the Django origin in dev (derived from `VITE_API_BASE_URL`) and leaves them relative in prod (same-origin). **Static FAQ/nav still live in plain JS**: `data/faq.js` (`getFaqs(locale)` returns flattened `{en,zh}`→string) and `data/nav.js` (`{ labelKey, path }`).
- **`Products.vue` layout**: left category sidebar + right 3-column thumbnail grid (responsive: 3 → 2 → 1 col; sidebar becomes horizontal chips ≤768px). Clicking a category **filters** client-side (all products are fetched once, grouped by category); the default "全部" view renders every non-empty category as a group. `activeSlug` drives it, kept in sync with the URL hash (`/products#<category-slug>`) so `Home`/breadcrumb links deep-link into a filtered view — handled in `onMounted` + a `watch` on `route.hash`.
- **Product images are never cropped.** Thumbnail frames are **portrait `3/4`** with `object-fit: contain` (products are 3.6~4.7:1 vertical cylinders — a 4:3 landscape frame cropped their ends off). `Products.vue` fetches `fetchProductScales()` and sets each `<img>`'s `max-width/max-height` to that percentage，所以**缩略图的大小顺序与实物一致**（滤芯与滤壳两棵树的比例经过 γ=0.5 压缩，见上）。 `ProductDetail.vue` also uses `contain` but **deliberately does not apply the scale** — a detail page shows one product with nothing to compare against, so shrinking it just floats a small cartridge in a big white box.
- **`HomeBanner.vue`** (Swiper): use **`rewind`, never `loop`**. Swiper's loop physically relocates slide DOM nodes, which fights Vue's keyed `v-for` reconciliation — with `loop: true` the whole carousel freezes (`realIndex` stuck, arrows/bullets/autoplay all dead). Reproduced on swiper **11.2.10 and 14.0.6**, so it is not a version issue. Also: **swiper must stay ≥14** — 11.x is covered by a critical prototype-pollution advisory (GHSA-hmx5-qpq5-p643, affects 6.5.1–12.1.1) and 14 still ships `swiper/vue`. Arrow/bullet colours follow the active slide's `theme` via a class on the Swiper root, updated **only in `@slide-change`** — mutating reactive state inside Swiper's init (`@swiper`) makes Vue re-render mid-measurement and leaves `slidesGrid = [0, null]`, locking the carousel.
- **About page certificates carry attribution.** `About.vue` renders `fetchCertificates()` as cards grouped into 本公司自有 / 供应链伙伴, each showing **持证方 + 适用范围 + 发证机构 · 编号 · 日期**, image `contain` (a certificate is a document — never crop it), click opens the full scan. This is deliberate: of the six certificates supplied, **none is issued to the company itself** (NSF 42 → Anhui Chiro Technology 滤芯供应商; CE/LVD/RoHS → 宁波馨颢 UV 设备; two ISO 9001 → 宁波馨颢 and Vontron, both expired 2015/2006 and hidden by default). Overseas buyers verify certificate numbers with NSF/SGS, so labelling the real holder is both honest and more persuasive. **Do not reword this into "our certifications".**
- **i18n** (`i18n/index.js`, vue-i18n, `legacy: false`, `globalInjection: true`, `fallbackLocale: 'en'`): UI-chrome strings are in `locales/en.js` / `locales/zh.js` / `locales/es.js`, namespaced per view (`nav.*`, `home.*`, `contact.*`, …). 支持的语言列在 `SUPPORTED_LOCALES`（`['en','es','zh']`），`LOCALE_LABELS` 是按钮文字、`HTML_LANG` 是 `<html lang>` 与 Intl 地区码；`LanguageSwitcher.vue` 按这个数组渲染，**加语言不用改组件**。Initial locale = `localStorage['klfilter-locale']`，否则取 `navigator.language` 的主语言子标签（`es-MX` → `es`），都不匹配则 `en`。

**不报错也不白屏**，只是那个接口悄悄换回中文。前端的白名单在

#### 数据列

`core.Category`（name / short_description）、`core.Product`（七个文案字段）、
`core.ProductImage.caption`，以及 `banner.Banner`、`homepage.Certificate`、
`downloads.Document`、`variants.ProductVariant` 的文案列，都加了 `*_es`。

- **`Certificate.issuer` / `holder` 刻意没有多语列**：那是发证机构与持证公司的法定全名，
  海外买家要拿去 NSF / SGS 核验，翻译等于改掉证据。

#### 译文的单一事实来源是 `homepage/data/es/`，由 `translate_site_to_es` 落库

数据文件的每个条目是一对 `{"en": 英文原文, "es": 西班牙文}`，**索引是英文原文本身**，
不是产品 slug。这么设计换来三件事：① 自动去重（351 个有「应用」的产品只有 174 种写法）；
② **同事改了英文，这条就查不到译文了**，于是不会写入一份和英文对不上的西班牙文，
而是老老实实出现在报表的「尚未翻译」里；③ 改一处，用到这句话的所有产品一起生效。

**落库前逐条机器验**，任何一条不过就拒绝写这一条并在报表里点名：行数不变、
**数字序列逐字相同**、规格每行的冒号位置不变、译文非空且不等于原文
（真不用翻的在数据文件里显式写 `"same": true`，不要往代码里加白名单）。
数字那条最有用——实测拦下过 7 处真实错误，全是西班牙语语序把型号和尺寸调换了位置
（`SUS304 de 120 mesh` 把 304 排到了 120 前面、`elemento 3013 de 13"` 同理）。

    python manage.py translate_site_to_es              # 只出报表
    python manage.py translate_site_to_es --missing out/   # 导出还没翻的英文原文
    python manage.py translate_site_to_es --apply      # 写库（幂等）

**留空是安全的**：接口按 `FALLBACK` 自动回退英文，前台不会开天窗。

#### ✅ 按语言分路径（2026-09-11 上线，此前这里写着「注入只有英文」）

```
/products/fc-53        英文（默认语言，**不带前缀**）
/es/products/fc-53     西班牙文
/zh/products/fc-53     中文
```

- **默认语言不加前缀是硬要求**，不是风格选择：`i18n_patterns(prefix_default_language=False)`。
  站点上线至今被 Google 收录的那批网址全是英文，改成 `/en/...` 等于让它们整体改道、
  排名从头再来。上线实测：453 个旧网址逐字节未变，只多了四行 hreflang。
- **`settings.LANGUAGE_CODE` 因此必须是 `'en'`**。⚠️ 它同时也是**后台界面**的语言，
  所以 `adminui/middleware.py:AdminChineseMiddleware` 把 `/admin/` 单独钉回 `zh-hans`
  （必须排在 `LocaleMiddleware` **之后**，中间件按顺序处理请求，放前面会被覆盖）。
  公开站的 `LANGUAGES` 用裸 `'zh'` 是为了网址是 `/zh/` 而不是 `/zh-hans/`，
  而 Django 只为 `zh_Hans`/`zh_Hant` 附带界面翻译，裸 `'zh'` 会静默落回英文——
  两边用不同的码是刻意的。`adminui/tests.py:AdminLanguageTests` 盯着这条链子。
- **✅ 「无前缀网址会不会被 Accept-Language 跳走」这条风险在结构上不存在**：
  `django/middleware/locale.py` 的 `process_request` 在「没有语言前缀 + 用了 i18n_patterns +
  未给默认语言加前缀」时**无条件**取 `LANGUAGE_CODE`，完全不看 Accept-Language/session/cookie；
  那段「404 时补前缀再重定向」只在 `prefix_default_language=True` 时才进。上线后实测三种
  Accept-Language 都是 200 + 英文。
- **hreflang 三处生成，取值必须一致（都是裸码 `en`/`es`/`zh`）**：
  服务端 `seo/views.py:_alternate_tags`、客户端 `frontend/src/seo.js:setAlternates`、
  sitemap 用 Django 自带的 `Sitemap.i18n/alternates/x_default`（后者直接取
  `settings.LANGUAGES` 里的码，所以另外两处不能写 `zh-CN`）。
  `<html lang>` 是另一回事，用更精确的 `zh-CN`，与前端 `i18n/index.js:HTML_LANG` 对齐。
- **🚨 canonical 指向别处的页面一条 hreflang 都不发**，也不进 sitemap。
  一边说「别收我」一边说「我是西语版」是自相矛盾的信号。实测线上 26 个这样的产品
  （长度组成员）。`seo/views.py:product_detail` 与 `ProductDetail.vue` 两处同一条规则。
- **前端：网址是语言的唯一事实来源**。`frontend/src/i18n/paths.js` 管前缀换算
  （**刻意不依赖 vue/window**，`node frontend/src/i18n/paths.test.mjs` 可直接跑，
  本仓库前端没有测试框架，这是唯一一份能真正验证的自测）；
  vue-router 用 `createWebHistory(ROUTER_BASE)`，**路由表一个字没改**。
  localStorage 降级成「记住上次的选择」，只在路径恰好是 `/` 时把访客送到偏好语言的首页，
  深链接一概不碰——否则同一个网址显示什么取决于访客浏览器，那就是 cloaking。
- **语言切换条必须是真 `<a href>`**，不能是 `<button>`：搜索引擎要顺着链接才能发现
  另外两种语言的页面。

上线实测（2026-09-11）：sitemap 453 → **1359 条**（453 × 3），每条 4 个 `<xhtml:link>`；
三份页面的 hreflang 互相指认且完全一致；数据 519/473/53/500/0 零变化。

#### 其它

- FAQ 的西班牙文在 `frontend/src/data/faq.json` 里加 `es` 键（与 `en`/`zh` 并列）。
  `faq.js:localize` 缺键回退英文，纯增量；`seo/render.py` 的 `LANG='en'` 不受影响。
- `seo/tests.py:LocaleParityTests` 盯着三份语言包逐键对齐（含数组下标）。缺键 vue-i18n
  会静默回退英文——整页西班牙文里冒出一句英文，很难被看出来。它把 `locales/*.js`
  转成 JSON 再解析（`_js_object_to_json`），**不支持反斜杠转义与模板字符串**，
  真用了会当场报错而不是静默半解析。

- **Switching locale reloads the whole page** — `setLocale()` persists the choice to `localStorage` then calls `window.location.reload()`; it does **not** reactively re-render. This is deliberate: in the Vite dev module graph the i18n instance gets duplicated, so runtime locale mutations don't propagate across all components; a reload re-boots every component in the freshly-detected locale, which is reliable in both dev and production. Do **not** rewrite this into in-place reactive switching without first solving the duplicate-instance problem.
- **标题区（eyebrow + 标题 + 简介）不限宽，与容器同宽**。全局 `.section-heading`（`style.css`，8 处在用）
  原本是 `max-width: 640px`，`Products.vue` 的 `.page-intro p` 是 `65ch`，`About.vue` 的 `.lead` 是 `70ch`
  ——三者一起造成「产品页标题 1168 而简介只有 570」的不等宽。2026-08-07 全部删掉，统一为容器宽（1152）。
  实测中文简介 39~65 字全部一行放得下，英文最长 264 字符占 2 行（原来 4 行）。
  **刻意保留的限宽**：`.cert-group-note`/`.cert-note`(80ch)、`Home.vue` 的 `.cta-inner p`(60ch)、
  `.footer-blurb`(40ch)、`HomeBanner` 的 18ch/46ch——它们不是标题简介，各有版式理由。
- **🚨 grid/flex 子项的默认 `min-width: auto` 会把「局部横滑」变成「整页横滑」**。
  `Products.vue` 的 `.chip-row` 用 `overflow-x: auto` + `flex: none` 的 chips 实现一行横滑，
  但它的父级 `.category-chips` 是 `.products-layout` 这个 grid 的直接子项，
  min-width 默认 auto → 被撑到内容最小宽度（4 个 chip 共 452px）→ 网格轨道 452px
  超出 375px 视口，**整个产品页在手机上可以左右拖动**。加 `min-width: 0` 解决
  （`.products-main` 早就有这一行，当初只修了右边那一列、chips 那列漏了，2026-08-07 才补上）。
  **判据是 `document.documentElement.scrollWidth > clientWidth`**；
  逐个元素查 `getBoundingClientRect().right > clientWidth` 能定位到具体是谁撑的。
- **Two vue-i18n gotchas already hit** (watch for these when editing `locales/*.js`): (1) a literal `@` in a message is vue-i18n "linked message" syntax and crashes message compilation — escape it as `{'@'}` (see the `email` value); (2) named interpolation such as `$t(key, { year })` on a runtime string message can fail to compile in the bundler build — the footer copyright avoids it by interpolating the year in the template instead of the message.

## Django 后台的左侧菜单（`adminui/`，2026-08-06 起）

后台左侧**不再按 Django 应用分组**，而是 10 个模型的平铺列表。原因：`banner`/`downloads`/
`productimages` 这几个应用各自只有一个模型，分组名和模型名重复，每次都要多点一次折叠。

`adminui/` 是无模型卫星应用，在 `AppConfig.ready()` 里给 `settings.SIMPLEUI_CONFIG` 赋值
（settings.py 求值时 admin 注册表还是空的，写死在那里读不到模型）。
**`'adminui'` 必须放 `INSTALLED_APPS` 末尾**——它依赖 `django.contrib.admin` 先
`autodiscover_modules('admin')` 把所有应用的 `admin.py` 导入完。

- **「平铺」的判据是菜单项不带 `models` 键**（`simpleui/static/.../js/menu.js:11` 的
  `v-if="!item.models"`）；`SIMPLEUI_CONFIG` 里 **`system_keep` 必须为 `False`**，
  否则是「默认分组菜单 + 自定义菜单」两份叠加（`simpletags.py:296`）。
- **菜单从 `admin.site._registry` 自动生成**，`MENU_ORDER` 只管顺序，不在表里的模型
  自动追加到末尾。刻意不写死一张表——那等于又造一个「新增模块必须记得同步改这里」的陷阱
  （本仓库已在 nginx 路由枚举、`seo/sitemaps.py` 上踩过两次）。名称取
  `Meta.verbose_name_plural`，不另外维护中文名。
- **🚨 权限行缺失会让菜单项对所有人（含超级用户）静默消失**：simpleui 的
  `get_filtered_menus` 比对的是 `user.get_all_permissions()`，那个集合是**按 Permission
  表的行**算的，**不是 `has_perm()`**（超级用户的 `has_perm` 恒为 True，但
  `get_all_permissions` 只返回表里真实存在的行）。实测踩过：`downloads` 的权限行还没建出来时，
  「技术文档」就从菜单里消失了，页面上毫无报错。权限行由 `migrate` 的 `post_migrate` 建。
  `adminui/tests.py` 有一条测试盯着每条 `permission` 都真实存在（典型触发场景是模型
  自定义了 `default_permissions` 却漏掉 `view`）。
- 自定义 `menus` 后**只有带 `permission` 键才会做权限过滤**，一个都不带就是所有员工看到
  全部菜单项。所以每项都带 `<app_label>.view_<model>`。

- **验证办法**：后台要登录，浏览器里不好自动化。用 Django 测试客户端走完整栈渲染即可——
  `Client().force_login(u); c.get('/admin/', HTTP_HOST='localhost')`，

  ⚠️ **只看菜单文字会得到假阳性**：旧的分组菜单展开后子项文字与平铺版完全一样，

### 产品 xlsx 批量导入：空格子 = 不动（2026-09-03 起，`adminui/resources.py`）

同事导出产品表、只改几格再传回来，每一行都报
`(1048, "Column 'certifications_zh' cannot be null")`。
**看着像「缺少这一列」，其实恰恰相反——表里有这一列，只是格子空着。**
openpyxl 把空单元格读成 `None`；而 `ModelResource.WIDGETS_MAP` 只映射了 `CharField`，
`TextField` 既不在表里也不是 `CharField` 的子类，于是落到默认的 `widgets.Widget`，
它的 `clean()` 就是 `return value`，`None` 原样透传，写进 NOT NULL 的列就是 1048。
（`CharField` 那条路径会拿到 `allow_blank=True`，空值变成 `''`，所以 `code`/`name_zh`
留空反而没事——**只有 `TextField` 会炸**，`order`/`is_published`/`category` 则是另外两种死法。）
报的是 `certifications_zh` 只因为它是那条 UPDATE 里**第一个**为空的列，
补上它下一个空列会接着报，一列一列打地鼠。

⚠️ **「缺列」与「空格子」是两件事，别记混**：缺列一直是允许的——
`Resource.import_field` 对不在表头里的列直接 return，只有 `import_id_fields`（`slug`）
缺失才硬报错。所以卡住批量修改的从来只有空格子。

`adminui/resources.py` 的 `PartialUpdateMixin` 从外部接管**导入**（`core/` 不能改）：
空格子跳过、`[清空]` 才真清空（且只对 `blank=True` 的文本列生效）、
`slug` 找不到就报错**不新建**（一个错别字就是一个前台可见的半空产品）。
**只换导入不换导出**（`get_import_resource_classes`），导出仍是 core 的全字段表，
「导出 → 删列 → 改几格 → 传回」这个用法才成立。
⚠️ 不能写成 `resource_classes = [...]`：core 已经设了 `resource_class`，
两个同时存在时 import_export 直接抛 `Only one of ... can be set`。

- **错误分三处放，只看一处会漏**：`import_field` 抛的 `ValueError` 被
  `import_instance` 包成 `ValidationError` 进 `result.invalid_rows`；
  其它异常（含 1048）进 `row.errors`；表头问题进 `base_errors`。
- **一行出错整批回滚**（import_export 把整个导入包在一个事务里），
  所以「改完红字那几行再整表重传」是唯一正确的用法，别去猜哪几行进去了。
- 导入页顶部那句「此次将导入以下字段：…」正是误导同事的源头，
  已用 `import_template_name = 'adminui/product_import.html'` 在下面补了一段填表说明。
  **不要去覆盖 `admin/import_export/import.html`**——应用模板目录按 `INSTALLED_APPS`
  顺序查找，`import_export` 排在 `adminui` 前面，同名文件会被它压住（而且会递归 extends）。

## Environment quirks (Windows-specific — read before running commands)

- Python deps live in `.venv/` (Python 3.13). Node deps live in `frontend/node_modules/` (Node.js v24 LTS, installed at `C:\Program Files\nodejs`).
- **Shell state does not persist between tool invocations in this environment.** `.venv` activation and PATH updates from installing Node do not carry over to a fresh shell/process. Practical implications:
  - Prefer calling venv binaries directly rather than relying on activation: `.venv\Scripts\python.exe`, `.venv\Scripts\pip.exe`.
  - In Bash (Git Bash), Node isn't on PATH by default in an already-open shell — prefix commands with `export PATH="/c/Program Files/nodejs:$PATH"`.
  - In PowerShell, if `node`/`npm` aren't found, refresh from the registry first: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`.
- `.claude/launch.json` defines two preview server configs, `django` and `frontend`. The `frontend` config intentionally invokes `node.exe` directly on `frontend/node_modules/vite/bin/vite.js` (instead of `npm.cmd run dev`) — `npm.cmd` internally shells out to a bare `node` command, which fails under the preview launcher's process because that process's PATH predates the Node.js install and isn't refreshed. If Node is reinstalled/upgraded, keep this direct-invocation pattern.
- `requirements.txt` **exists** (no `pyproject.toml`). Backend packages: `Django==6.0.7`, `djangorestframework==3.17.1`, `django-cors-headers==4.9.0`, `django-simpleui==2026.1.13`, `mysqlclient==2.2.8` (MySQL driver), `gunicorn==23.0.0` (production WSGI server), `Pillow==11.3.0` (`ImageField` + 全部图片处理), `django-import-export==4.3.10` + `openpyxl==3.1.5` (admin Excel/xlsx import-export **and** the `import_offer_lists` command). Frontend deps: `vue`, `vue-router`, `vue-i18n`, `axios`, **`swiper@^14`**（见前端章节，不要降到 11）。
- **⚠️ `git archive` 打包会把行尾变成 CRLF**（本机 `core.autocrlf=true`）。仓库 blob 是 LF、
  磁盘工作区也是 LF，**但导出的 tar 包里全是 CRLF**——解包到服务器后每个 `.sh` 的
  `set -euo pipefail` 变成 `pipefail\r`，bash 报 `set: pipefail: invalid option name` 当场退出。
  2026-08-05 实际踩到：一次部署把服务器上四个 `deploy/*.sh` 全弄坏了，包括每日备份
  `backup.sh`、每周恢复演练 `verify_backup.sh`，以及**应急回滚 `rollback.sh`**——
  出事时最需要的那个反而跑不起来，且在有人手动跑之前毫无迹象。
  已加 `.gitattributes`（`*.sh` / `Dockerfile` / `*.conf` / `.dockerignore` → `eol=lf`）堵住源头。
  **排查提示：Git Bash 的 `sed`/`od` 会做文本模式转换，读出来看不到 `\r`，结论不可信。**
  要用 Python 直接数字节：`b.count(b'\r\n')`。
  **2026-09-01 起云服务器改用 `git clone` / `git pull`，不再有"打包再解包"这一步，
  这条从源头上不会再发生。** 但只要还会往服务器单发 `.sh`（比如用 SFTP 传一个脚本上去），
  就仍然要在写入前显式把 CRLF 全部换成 LF——本次迁移把 `pull_from_cloud.sh` 传上 NAS 时就是这么做的。
- **`.bat` 的要求跟上面正好相反：CRLF + UTF-8 无 BOM**（`.gitattributes` 已加 `*.bat text eol=crlf`）。
  LF 结尾的 bat 在 cmd.exe 下 `goto`/标签不可靠；带 BOM 时 cmd 会把 BOM 当第一条命令的一部分而报错。
  中文提示还需要首行 `chcp 65001 >nul`，否则在默认 GBK 代码页下是乱码。
  注意与 `.ps1` 区分：**PowerShell 5.1 反而要求 UTF-8 with BOM**（见备份脚本那条），两者别记混。
- **🚨 `frontend/.env.development.local` 会静默改掉整个前端的 API 地址**（2026-09-03 实际踩到）。
  vite 的 env 优先级是 `.env.development.local` > `.env.development`，而这个 `.local` 文件在
  `.gitignore` 里、`git status` 看不见，翻代码永远找不到原因。
  症状极具迷惑性：**只有产品页/首页坏，FAQ、关于、联系这些静态页照常显示**——因为只有前者调
  `/api/`。而 `fetchCategories` / `fetchProducts` 不是 fail-open（其余四个卫星接口都是），
  一挂整页就落到「产品加载失败，请稍后重试」。
  本次是 09-02 为了把开发服务器开给局域网同事，写了
  `VITE_API_BASE_URL=http://192.168.5.160:8000/api`，事后没删；而 Django 按
  `.claude/launch.json` 跑的是 `runserver 8000`（**只绑 127.0.0.1**），于是 6 个接口全是
  `ERR_CONNECTION_REFUSED`。
  **判据是看浏览器 Network 里请求打到哪个地址**，不是看 `.env.development`。
  服务端全绿（`curl http://127.0.0.1:8000/api/products/` 200）却说前台加载不出来时，先查这个文件。
  ⚠️ **真要开局域网共享，四件事缺一不可**：① 这个 `.local` 文件；② vite 加 `--host`
  （默认只绑 `[::1]`，同事根本连不上）；③ Django 改 `runserver 0.0.0.0:8000`；

  `runserver 8000` 和 vite `:5173` → 开浏览器），Python 与 node 都走全路径，理由同 `.claude/launch.json`。
- **多层引号会炸**（PowerShell → paramiko → bash → docker exec）。给服务器跑多行脚本时，**写成 `.sh`/`.py` 文件用 SFTP 传上去再执行**，不要试图把它塞进一行命令里。`python manage.py shell -c "…"` 只在整条命令没有单引号时才可靠。

## Deployment (production — 阿里云轻量 + Cloudflare Tunnel)

The site is live at **https://www.kl-filter.com** and **https://kl-filter.com** (migrated off a former Squarespace site). Topology is **same-origin**: nginx serves the built Vue SPA at `/` and reverse-proxies `/api/` + `/admin/` to Django (gunicorn). TLS is terminated at Cloudflare's edge; a **Cloudflare Tunnel** (`cloudflared`) connects the server outbound to Cloudflare, so **no inbound port is open** and there is no CORS in prod.

- **🚨 上线前后要比对产品数据，只数总数不够**——字段被改是看不出来的。
  **迁云那次用的办法（推荐沿用）**：不硬编码字段名，遍历 `_meta.concrete_fields`
  给每一行算 SHA256，输出 `MODEL/ROW` 两种行，两边 diff：
  ```python
  # docker compose exec -T web python manage.py shell <<'PY'
  import hashlib
  from django.apps import apps
  SEP, END = chr(0), chr(1)          # 用数据里不可能出现的字符做分隔，避免拼接产生歧义
  for app_label, model_name in [('core','Product'), ('core','Category'),
          ('core','ProductImage'), ('core','Contact'), ('banner','Banner'),
          ('homepage','CategoryCard'), ('homepage','Certificate'),
          ('downloads','Document'), ('variants','ProductVariant'),
          ('productimages','ImageScale')]:
      M = apps.get_model(app_label, model_name)
      fields = sorted(f.attname for f in M._meta.concrete_fields)
      for o in M.objects.all().order_by('pk'):
          h = hashlib.sha256()
          for f in fields:
              h.update((f + SEP + str(getattr(o, f, None)) + END).encode('utf-8', 'replace'))
          print('ROW', app_label + '.' + model_name, str(o.pk) + '|' + h.hexdigest()[:16])
  ```
  **media 也要逐文件比**（避开 `find -printf` 的转义，直接用 `stat`）：
  ```bash
  docker compose exec -T web sh -c "cd /app/media && find . -type f | LC_ALL=C sort | xargs stat -c '%s %n'"
  ```
  两边各导一份再 diff。
  2026-09-01 实测：1222 行数据指纹 + 1127 个媒体文件，唯一差异是
  `Document.download_count`（画册下载计数，一直在涨），其余零差异。
  ⚠️ **别用 `du -sh` 比 media 大小**——不同文件系统的块分配不同，实测 NAS 报 136M、
  云上报 95.1M，而逐文件比对是完全一致的 1127 个文件 / 92.9 MB。

## 公司共享文件的备份（2026-09-04 起，与网站无关）

`Z:` 盘（`\\192.168.5.172\团队文件-业务部` = `/vol1/@team/业务部`，实测 **9.6 GB / 7457 个文件**）
与 `团队文件-技术部`（`/vol1/@team/技术部`，现在几乎是空的）此前**一份备份都没有**，而它们所在的阵列
`md0 : active raid1 sdc1[0]` 是 **`[1/1]`——名义 RAID1 只有一块盘，零冗余**。
`网站维护.md` 12.7 早把这条列为「和网站无关但优先级更高」的隐患。现在补上了，两级、各 3 天：

| 位置 | 时刻（北京时间） | 做什么 | 保留 |
|---|---|---|---|
| **NAS** `192.168.5.172` | 20:00 | `deploy/nas_shares_backup.sh`：`/vol1/@team/*` → **另一块盘** `/vol2/1006/share-backup/<日期>/` | **3 天** |
| NAS | `@reboot` | 同脚本 `--if-missing` 开机补跑 | — |
| **办公电脑** | 次日 13:10 | `deploy/共享文件备份.ps1` → `deploy/pull_shares.py`（robocopy over SMB）→ `D:\NAS共享备份\` | **3 天** |

**这套东西和网站没有任何关系**，只是复用 `deploy/` 里已有的约定
（`STATUS.txt` 成败标记 / `trap ERR` / 先轮转再写入 / `.partial` 落地 / 桌面告警文件）。
纯逻辑抽在 `deploy/backup_checks.py`，`deploy/tests.py` 有 16 条用例盯着。

- **保留的是 3 份完整独立副本**，不是「镜像 + 变更历史」，也**不用硬链接**——
  沿用 `pull_backup.py` 已确立的原则：*备份的独立性比省盘重要*。
  代价是每天在盘内真的复制一份 9GB；网络上只走当天差异（**实测日变化仅 24 个文件 / 30MB**）。
- **🚨 NAS 侧第一条守卫是「源与目标不能在同一个文件系统」**（`stat -c %d` 比对）。
  源盘 sdc 恰恰是那块没有冗余的盘，写在同一块盘上只防误删、不防盘坏，
  而防盘坏正是做这件事的首要理由。
- **共享的真实路径不写死**，默认枚举 `/vol1/@team` 下的每个子目录（`--where` 只打印解析结果）。
  不写死清单是刻意的：以后同事新建部门共享会自动被保护，写死的话它会静默地一直没备份。
  ⚠️ **别改成"从 smb.conf 解析"**——实测 fnOS 的 `/etc/samba/smb.conf` 里只有 `[global]`，
  共享段在它自动生成的 `/etc/samba/users/<uid>.share.conf`（`include = …/%Y.share.conf`），
  那些文件由 fnOS 重写，不是稳定接口。另注 **SMB 共享名与磁盘目录名不一样**
  （`团队文件-业务部` → `/vol1/@team/业务部`），备份里用的是磁盘上那个名字。
- **🚨 `bytes=` 求和必须 `printf "%.0f"`，不能用 awk 的 `print`**。实测踩过：
  NAS 上是 Debian 默认的 **mawk**，`OFMT` 是 `%.6g`，9,581,327,274 字节被打印成
  `9.58133e+09`，清点行匹配不上 → **最大的那个共享被静默跳过、完全没有对账**，
  而两边都不报错。本机 Git Bash 的 gawk **不复现**这个格式，光在开发机上试是试不出来的。
  `backup_checks.unparsed_share_lines` 现在会把"有清点行却解析不出来"变成一条明确告警。
- **`claude` 在 NAS 上没有免密 sudo**（和云服务器不同），所以这套东西全程不需要 root：
  源只读、目标 `/vol2/1006/` 本来就是 claude 自己的空间。
- **🚨 robocopy 的退出码是位掩码，判据是 `< 8` 而不是 `== 0`**。
  一次正常的增量同步几乎必然返回 1（复制了文件）或 3（还删了多余项）；
  写成 `== 0` 会让桌面天天躺着一个「异常」文件，最后没人再看它——那比不告警更糟。
  负数（被 Ctrl-C 打断）也必须判失败，它不是位掩码，直接和 8 比会算成「成功」。
- **robocopy 的参数每一个都有理由**：`/R:1 /W:2`（默认是 `/R:1000000`，
  碰上一个被 Excel 锁住的 `~$xxx.xlsx` 能重试到天荒地老）、`/FFT`（Linux 那侧时间戳
  精度 2 秒，不加会天天全量重传，等于限速白设）、`/UNILOG+`（日志走 UTF-16，
  全中文路径用 ANSI 日志会变乱码，出事时最需要读的东西反而读不了）、
  **不用 `/MT`**（多线程会瞬间打满 2.4GHz 信道，正是「全员掉线」的放大器）。
  限速只能靠 **`/IPG`**（默认 60ms ≈ 1MB/s，`KLIPG=0` 解除）。
- **🚨 轮转永远不删「最新的那一份」，哪怕它已经过期**。办公电脑经常关机好几天
  （实测 08-18~08-20 关了三天），回来时本地几份全都超窗；若当天拉取又恰好失败，
  按日期一刀切会让这台机器**一份备份都不剩**，而这一步不会有任何报错。
  `backup_checks.expired_date_dirs` 里有守卫，有测试盯着。
- **落地前必须对账**：拿 NAS `manifest.txt` 里的「每个共享的文件数 + 字节数」比一遍，
  任一不符就丢弃这一份。只比目录总大小是不够的——少拷了几百个小文件，
  总大小看起来几乎没变，而那几百个文件确实就没了。
- **办公电脑那份天然比 NAS 慢一天**（NAS 20:00 出快照、办公电脑次日 13:10 才拉）。
  这是刻意的：这台电脑夜里多半关着，把任务排到 20:00 之后只会天天靠
  `StartWhenAvailable` 补跑，反而更不确定。
- **排除清单实测会滤掉 585 个文件**（7457 → 6872）：379 个 `.tmp`、205 个 `~$` Office 锁文件、
  1 个飞牛同步的临时库，外加 fnOS 内部目录 `.@#local`（411MB，samba 用 `veto files` 藏着，
  同事在 Z: 上根本看不到它）。**逐条 diff 核对过，没有真实资料被吞掉**——
  以后再动排除清单，用同样的办法比一遍再上线。
- **2026-09-04 首次上线实测**：NAS 侧全量 9.0G 耗时 **110 秒**（盘内复制，不走网络），
  `/vol2` 还剩 432G；清点 `share=业务部 files=6872 bytes=9581327274`，
  与 rsync 自报的 `Total transferred file size: 9,581,327,274 bytes` 一字不差。
- **首次种子 9GB 必须下班后跑**（`-Seed`，不限速约 50 分钟）。
  平时不限速跑会把办公室 Wi-Fi 信道占满——2026-08 已经因为网站那个拉取脚本
  发生过一次全员掉线，判据是**拉取期间网关 ping 是否平稳**，不是「拉取有没有成功」。

## 从抠图图库批量上传产品（2026-08-21 起）

`Z:\工作\新网站\抠图` 有约 340 张产品照片，**子目录结构就是分类树**，
叶子目录里是「若干产品图 + 一张分类集合图」——同事正是把那张集合图当作
`CategoryCard` 上传的。滤芯 / 滤壳 / 沃顿RO膜三支同事在维护，配件 / UV /
净水器 / 迷你商用RO 四支则**一个产品都没上**（`accessories`、`whole-house-filter`、
`UV-sterilizer` 至今是 0 产品的空分类，却因为没有 `CategoryCard` 行而照常显示在前台）。

流程是 **AI 起草 → 人工核对 → 上架**，三个命令各管一段：

1. `report_image_gaps` 出差异报表交同事（只读）。它**不做兜底**：匹配不上又不在
   已知集合图清单里的一律单独列出，并在末尾打一行**账目**
   （`产品图 = 精确匹配 + 疑似 + 待新增 + 重复文件`），对不上就直接报错——
   这是为了守住「绝不静默吞掉文件」，`restructure_cartridge_categories` 上一版正是栽在这里。
   编号匹配的两个坑有测试盯着：**前缀切点必须落在非字母数字边界**
   （否则 `FC-8` 会匹配到 `FC-80`）、**短编号不做包含匹配**（`FC5` 落在 `FC55` 里）。
2. `stage_images` 按清单把原片转成 `<slug>.jpg`。原片里有 36–48MB 的 TIF，
   而 `attach_product_images` 的 `EXTENSIONS` 只认 `.webp/.jpg/.jpeg/.png`——
   **不要去放宽那个常量**，在暂存这一步转好格式即可。
   **对应关系从清单的 `源图片文件` 列读，不从文件名猜**：抠图目录的命名
   五花八门（`UV6W  UV11W.TIF` 一张图两个型号、`LP440 (2).jpg` 是拷贝、
   `FC-71.jpg.jpg` 双后缀），任何猜测规则都会在某处翻车。一张源图可以喂多个 slug。
3. `import_staged_products` 读清单建产品，按 slug 幂等，且**拒绝往有子分类的分类里挂产品**
   ——那样的产品在前台完全不可见且不报错。**上不上架只由 `--publish` 决定**，
   清单里的 `is_published` 列一概不读，免得改一个单元格就把一批产品推上线。
   图片不在这个命令里挂，落库后跑 `attach_product_images --dir <同一个目录>`。
   ⚠️ 挂图会逐张转 WebP，145 张要跑好几分钟，别以为是卡死了。
